# Облачный браузер Tilda: исследование и прототип

Дата: 27 октября 2026. Основной сайт и статьи остаются в Tilda.

**Приоритет изменён:** live-адаптер Playwright приостановлен до исследования
существующего [Tilda MCP](mcp-integration.md). Прототип остаётся резервным.

## Что действительно проверено

| Проверка | Результат |
| --- | --- |
| Официальная справка API, T123 и SEO Tilda | Получена и прочитана |
| Playwright Python в этой машине | Установлен, Chromium запускается headless |

Источники Tilda: [API](https://help-ru.tilda.cc/api),

Документация Playwright прочитана через **официальный** репозиторий Microsoft

## Возможна ли автономность

Технически Playwright работает в GitHub-hosted Linux runner без открытого
браузера на компьютере владельца. Браузер при этом существует и работает в облаке.
Сохранённая сессия может избавить от входа на каждом запуске, **если Tilda примет
её на другом IP/устройстве**. Это ещё не проверено. Гарантированного бессрочного
refresh-token интерфейса Tilda не установлено. Срок cookie не гарантирует срок
серверной сессии; MFA/CAPTCHA/отзыв или смена IP могут остановить сценарий.

Поэтому автономную публикацию 1 и 8 ноября 2026 обещать сейчас нельзя.
Условная реализация возможна после настоящего staging-теста создания черновика,
отдельно разрешённой тестовой публикации, восстановления сессии на runner,
проверки повторов/обложки и настройки долговечного журнала. GitHub schedule
может задержаться/не запуститься: 03:00 UTC — целевое время, не гарантия секунды.
Существующее расписание остаётся ТОЛЬКО dry-run.

## Авторизация без передачи пароля

1. Владелец запускает `scripts/capture_tilda_session.py` **на доверенном компьютере**
   в headed Chromium, вручную вводит логин/MFA в Tilda. В скрипте нет поля пароля,
   кодов MFA или автоматических кликов. Никаких кодов/паролей в переписку.
2. Скрипт открывает указанный владельцем URL проекта, владелец проверяет
   аккаунт/VericoMedia. `storage_state(indexed_db=True)` сохраняет cookie,
   localStorage и IndexedDB в `.auth/tilda-state.json` с правами 0600.
   sessionStorage по умолчанию не сохраняется. Его необходимость для Tilda
   пока неизвестна. Браузерные профили и пароли сохранять не надо.
3. Сессию считать полноценным доступом аккаунта. Предпочтительно отдельный
   пользователь с минимальными правами к нужному проекту, без общего доступа.
4. Маленький state-файл можно передать **напрямую с компьютера** в GitHub
   Environment `tilda-staging` через `gh secret set TILDA_STORAGE_STATE_JSON
   --env tilda-staging --repo verico26/vericomedia-publisher < .auth/tilda-state.json`.
   Вставлять файл в чат, git, Issues, Actions artifacts или cache запрещено.
   GitHub Secret имеет лимит 48 KB; большой state хранить в внешнем secret store
   с OIDC, не в публичном артефакте и не обрезать cookie наугад.
5. Будущий trusted-job получает state только из Environment Secret через env,
   Python читает `os.environ` без печати и передаёт dict в `new_context`.
   Если нужен файл — `$RUNNER_TEMP`, umask 077, удаление в finally/always. Никакой
   shell-интерполяции содержимого секрета, shell tracing, debug HTTP, HAR или trace.
6. Прежде чем резервировать статью, read-only preflight должен доказать: нет
   login/MFA/CAPTCHA, верный пользователь, project ID, права редактора и ожидаемый UI.
   Сам факт отсутствия /login недостаточен. Не прошёл — остановиться с
   `reauth_required`, никаких write-retry. Владелец повторно входит и заменяет secret.
   Отключать MFA/обходить CAPTCHA нельзя. Автообновление секрета не реализовано.

Required reviewers у Environment полезны для первого теста. Для будущего
автономного production-job потребуется отдельно согласованная политика: обязательный
ручной reviewer при каждом запуске несовместим с полностью автономным расписанием.
Текущий workflow не читает никаких secrets и не содержит Tilda job.

## Прототип создания страницы: границы и шаги

`browser_prototype.py` — исполняемая модель сценария с реальным Chromium.
`FixtureEditor` использует селекторы **только** из `tests/fixtures/editor.html`.
Это не копия DOM Tilda. `--target tilda` всегда возвращает ошибку до запуска браузера.
`config/tilda-ui.unverified.json` специально содержит null/verified=false: селекторы
редактора, CodeMirror/textarea, проект ID и признак сохранения ещё не исследованы.
Адаптер реального редактора не реализован. Пример image URL — заглушка, не реальная
обложка. По одному лишь имени VericoMedia нельзя безопасно выбирать проект.

После разрешения на один тестовый черновик реальный адаптер должен:

1. Пройти read-only preflight, проверить точный project ID и создать только
   страницу с согласованным `automation-test-*` slug. Не дублировать существующие
   страницы-шаблоны без отдельного согласования. Не редактировать главную страницу.
2. Проверить удалённый список страниц и журнал по ID статьи и slug, атомарно
   резервировать операцию до первого клика создания. Записать page ID сразу,
   как только он станет доступен, даже до заполнения полей.
3. Создать пустую страницу, задать title/slug, выключить индексацию. Уточнить,
   какие поля Tilda сохраняет автоматически: **черновик тоже изменяет проект**.
4. Настройки страницы → SEO → отображение в поиске: title и description.
   Настройки страницы → Соцсети: image/бейджик отдельно от SEO-текста.
5. Добавить T123, открыть его контент, заполнить HTML через реальный редактор,
   проверить чтение обратно и сохранение. Потребуется реальный UI, не догадки
   о name/id полей. Для синтетического HTML скриптов нет; произвольный контент
   до live-теста должен проходить отдельную allowlist-санитизацию.
6. Установить/прочитать изображение, перенести его в согласованный cover-блок
   или `<img>` T123 с alt, проверить отсутствие расхождений. Сохранить черновик.
7. Переоткрыть по page ID и проверить все поля/ровно один черновик. Скриншот
   только страницы результата; приватные панели, email, cookies маскировать.
   Снимать экран входа/MFA и публиковать full-page редактор в артефактах нельзя.
8. На этой стадии НЕ нажимать «Опубликовать», «Опубликовать все страницы»,
   не трогать настройки сайта/меню. Для публикации потребуется отдельное разрешение.

## Бейджик и обложка: это разные сущности

Справка подтверждает отдельный бейджик: Настройки страницы → Соцсети → Отображение
в соцсетях и мессенджерах. Обложка в теле статьи — отдельный блок или `<img>` в T123.
Tilda не обещает автоматически делать визуальную обложку из бейджика.

Предпочтительный вариант: один `page_image` в исходном материале устанавливается
в бейджик и в визуальную обложку, без кругового чтения страницы до её публикации.
Если источник именно **уже выбранный бейджик**, можно прочитать URL из UI его поля
(после проверки актуального DOM), затем подставить в cover. В макете чтение поля и
копирование в cover реально выполнены и сверены; в Tilda это пока гипотеза.

В API `getpageslist`/`getpage` документация показывает поля `img` и `featureimg`,
но в просмотренной справке нет достаточного описания их связи с бейджиком.
`badge_from_api_metadata` возвращает только **непроверенного кандидата**, не
провозглашает featureimg истинным бейджиком. На тесте сравнить UI URL, API поля и
`og:image` опубликованной страницы (только после разрешения на публикацию).
`og:image` не требует входа для публичной страницы, но до первой публикации
не существует/может быть старым; он не даёт новый бейджик черновика.

Нужно проверить HTTPS, стабильность CDN URL, размеры/кадрирование, alt и права
на изображение. Социальный preview и hero имеют разные пропорции. Будущая загрузка
по URL требует allowlist и защиты от SSRF; сейчас сетевого загрузчика картинок нет.

## Повторы, ошибки и дубли

Прототип повторяет только read/assertion шаги с ограниченным backoff. Создание,
сохранение и загрузка — по одному разу. При timeout после create claim остаётся
неразрешённым: повторный запуск блокируется до ручной сверки. Это проверено
реальным браузером на макете. Проверяются как удалённый slug, так и локальный
unique `(project,slug)` / `(project,article_id)`. Изменённый HTML не отменяет claim.

В CI SQLite не переживает новый runner. Для реальной автоматизации нужен общий
durable журнал, транзакции и unique constraints + сверка Tilda после неоднозначных
исходов. Существующая SQLite-реализация и concurrency недостаточны для production.
Скриншоты успеха/ошибок сейчас содержат только синтетические данные. Ошибки CLI
логируются по типу без state, URL с токенами и HTML. Tracing запрещён для live.

## Запуск и проверяемая альтернатива сетевым ограничениям

```sh
.venv/bin/python -m pip install -r requirements-browser.txt
.venv/bin/python -m playwright install --with-deps chromium
RUN_BROWSER_TESTS=1 .venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m vericomedia_publisher.browser_prototype
```

В текущей среде штатная загрузка Chromium с `cdn.playwright.dev` и
`playwright.download.prss.microsoft.com` получила 403 Domain forbidden.
Использован уже установленный `/usr/bin/chromium`:

```sh
RUN_BROWSER_TESTS=1 BROWSER_EXECUTABLE=/usr/bin/chromium .venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m vericomedia_publisher.browser_prototype --executable /usr/bin/chromium --output /tmp/verico-browser-demo
```

Совместимость системного Chromium подтверждена только этими тестами, штатный
matching build предпочтительнее. Повторный demo с тем же журналом намеренно
блокируется; для нового синтетического теста использовать новый output-dir,
а реальный unresolved ledger никогда не удалять ради повтора.

Проверяемая альтернатива: ручной workflow `browser-prototype.yml` на чистом
GitHub runner устанавливает штатный Chromium, выполняет весь набор с
`RUN_BROWSER_TESTS=1`, сохраняет только синтетические screenshots/result.json.
Ни сессия, ни SQLite, ни HAR/trace не входят в allowlist артефактов. В workflow
нет schedule или Tilda credentials. Запуск в GitHub ещё не проверен.

Для доступа к редактору в текущей среде нужны `tilda.cc` и реальные наблюдаемые
asset/auth домены. Разрешать домены по наблюдаемым отказам; wildcard всей сети
не требуется. Добавление сетевого доступа не даёт разрешения на запись.

## Действия владельца для первого настоящего теста

1. Отправить/проверить код в default branch и вручную запустить synthetic workflow.
2. Сообщить ID и URL проекта VericoMedia, согласованный тестовый slug/шаблон и
   источник изображения (это не секреты). Подтвердить допустимость browser automation.
3. Разрешить отдельно **создание одного неопубликованного черновика** в этом проекте.
   Сейчас такого разрешения нет; сам прототип ничего там не создаёт.
4. На доверенном компьютере сохранить сессию и передать напрямую в защищённый
   GitHub Environment. Пароль и MFA остаются только в браузере пользователя.
5. Настроить доступ runner/среды к Tilda. Сначала проверить сессию read-only с
   того runner, где будет работа; затем исследовать DOM и реализовать адаптер.
6. После успешного черновика отдельно согласовать одну тестовую публикацию,
   проверить T123/SEO/бейджик/обложку/дубли/откат. Только после принятия результата
   решать о production-расписании и постоянном хранилище.
