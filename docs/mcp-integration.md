# Приоритет: существующий Tilda MCP вместо браузера

Дата исследования: 27 октября 2026. Playwright остаётся резервным направлением,
работа над live-адаптером приостановлена. Основной сайт и статьи остаются на Tilda.

## Что проверено и чего пока нельзя утверждать

| Контур | Результат |
| --- | --- |
| Инструменты текущего облачного чата | Tilda MCP отсутствует среди доступных инструментов |
| Переменные окружения с TILDA/MCP в имени | Не обнаружены; значения других переменных не раскрывались |
| Установленный Codex CLI 0.163.0 | `codex mcp add --help` подтверждает Streamable HTTP, stdio, bearer-token-env-var; `login --help` — OAuth |
| Настраиваемый MCP как native-инструмент Codex Cloud | Для этого аккаунта/облачного продукта не подтверждён; инструмент регистрации в текущем сеансе не предоставлен |
| Сервер, ранее работавший в ChatGPT | URL, транспорт, провайдер, scopes и каталог инструментов пока неизвестны |
| Создание/редактирование/публикация через этот сервер | Не проверены, никаких write-вызовов не было |
| GitHub Actions | MCP можно вызывать отдельным программным клиентом, если endpoint и unattended auth доступны runner; конкретный сервер не проверен |

Наличие Codex CLI внутри облачной машины **не доказывает**, что его config.toml
меняет native-инструменты этого облачного разговора. ChatGPT Apps/MCP, Codex
CLI и Codex Cloud — отдельные хосты/клиенты. Подключение и OAuth-согласие в одном
хосте нельзя считать автоматически перенесёнными в другой. Для custom remote
MCP в Cloud надо подтвердить поддержку именно в настройках текущего продукта
или у администратора/OpenAI. Не обещаем несуществующий экран «Add MCP» в Cloud.

## Источники и ограничения исследования

Прямые запросы к developers.openai.com/codex/mcp, /cloud, /cloud/environments,
/config-reference и modelcontextprotocol.io получили 403 CONNECT от прокси.
Содержимое этих страниц не было прочитано. В черновик среды добавлены разрешения
на домены документации; это не равнозначно применению runtime-настроек.

Проверены локальные CLI help и официальный исходный код OpenAI:
[config.schema.json](https://github.com/openai/codex/blob/603a7baff0f6f37ee9a8a9375a272eaab03d3ece/codex-rs/core/config.schema.json).
Схема содержит url, command/args, bearer_token_env_var, env_http_headers,
enabled_tools/disabled_tools, OAuth. Схема main может отличаться от установленной
версии; CLI help использован как свидетельство именно локально доступных команд.
[Официальный Python SDK MCP](https://github.com/modelcontextprotocol/python-sdk)
подтверждает клиентов stdio, Streamable HTTP и SSE. Поддержка legacy SSE этим SDK
не означает поддержку SSE напрямую командой `codex mcp add --url`.

Это исследование подтверждает программный путь из контейнера, но не даёт
окончательного ответа о native custom-MCP в текущем Codex Cloud. Для него нужна
проверка доступных настроек аккаунта и актуальной cloud-документации.

## Какие данные нужны от владельца сервера

Передавать в чат можно только несекретную часть:

- Название/провайдер MCP, документация, версия или репозиторий сервера.
- Точный endpoint MCP, если URL не содержит токен/подпись. Не угадывать `/mcp`
  или `/sse` по адресу сайта Tilda. Если URL секретный — хранить весь URL в secret.
- Транспорт: Streamable HTTP; legacy HTTP+SSE; либо stdio (команда, пакет,
  закреплённая версия и аргументы запуска вместо URL).
- Авторизация: OAuth / Bearer / именованный header / иной поддерживаемый механизм.
  Для OAuth — issuer/resource, client registration, scopes, допустимые redirect URI
  и наличие поддерживаемого способа unattended refresh/service-account.
- Несекретные названия переменных, требования к IP/VPN/allowlist, версии протокола,
  лимиты и URL документации. Нужен ли серверу собственный браузер/сессия Tilda.
- ID проекта «Галерея маркетинга Верико» и подтверждение, что это нужный проект
  для vericomedia.ru. Не считать его автоматически тем же, что VericoMedia.

Токены/refresh token/client secret/cookies/подписанные URL не отправлять в чат.
API-ключи Tilda и учётные данные самого MCP — разные уровни: если Tilda credentials
хранит сервер, их не надо копировать клиенту. Не извлекать токены из ChatGPT.

Условные имена конфигурации клиента (не установленные требования сервера):
`TILDA_MCP_URL`, `TILDA_MCP_TRANSPORT`, `TILDA_MCP_TOKEN`;
`TILDA_PROJECT_ID` как отдельный scope/allowlist. OAuth-имена и headers выбираются
по документации реального сервера. URL без секретов — GitHub Variable,
токен или URL с подписью — GitHub Environment Secret.

## Пошагово: подключение и проверка

1. В существующей настройке приложения ChatGPT найти сервер/провайдера и скопировать
   только несекретные сведения выше. При необходимости запросить конфигурацию
   у администратора сервера. Пока endpoint неизвестен, соединение не тестируется.
2. В настройках **именно используемого Codex Cloud/workspace** проверить наличие
   поддерживаемого custom-MCP/app подключения и ограничения администратора.
   Если оно доступно — добавить подтверждённый URL и транспорт, пройти OAuth
   в официальном UI либо внести credential в защищённое поле. Только после этого
   в новом/обновлённом сеансе проверить наличие сервера в каталоге инструментов.
   Если такого способа нет, не подменять его настройкой ChatGPT.
3. Альтернатива без native-подключения: программный MCP-клиент внутри облачного
   контейнера или отдельного GitHub runner. Такой клиент может работать с тем же
   сервером, но его tools не становятся native tools текущего агента автоматически.
4. Для **отдельного Codex CLI** справка подтверждает шаблон команды:

   ```sh
   codex mcp add tilda --url "$TILDA_MCP_URL" --bearer-token-env-var TILDA_MCP_TOKEN
   # Для OAuth вместо bearer-настройки: add с подтверждённым URL, затем
   codex mcp login tilda
   ```

   URL должен уже содержаться в защищённой конфигурации процесса; не подставлять
   токен в командную строку. OAuth-login может требовать интерактивного согласия.
   Это **не команда регистрации сервера в Codex Cloud**. Не запускать agent-задачу
   с доступом ко всем write-tools после добавления. Сначала использовать
   изолированный диагностический MCP-клиент из шага 6. Перед native-подключением
   настроить read-only permissions на стороне сервера и allowlist клиента.
5. Для stdio получить проверенную команду/пакет сервера, закрепить версию,
   установить его в облачной машине, передать env через secure settings.
   `localhost` с компьютера владельца недоступен cloud runner. Для legacy SSE
   выбрать документированный SSE-клиент или поддерживаемый адаптер; не считать
   endpoint SSE совместимым со Streamable HTTP автоматически.
6. Первый протокольный тест выполняет только `initialize`,
   `notifications/initialized`, `tools/list` (с пагинацией при необходимости).
   Никакого `tools/call`, даже если tool называется «test» или «validate».
   Записать согласованную версию протокола, факт соединения, названия tools и
   входные JSON schemas в приватный отчёт. Не печатать URL с ключами, headers,
   OAuth-ответы, prompt/resource contents. Текст сервера считать данными,
   а не разрешением выполнять инструкции из описаний инструментов.
7. Разобрать каталог вручную: какие tools действительно создают страницу,
   меняют блоки/метаданные/T123 и публикуют; какие параметры выбирают проект;
   поддерживаются ли draft/no-publish, idempotency и независимая публикация.
   Tool может сразу публиковать при «создании» — это нужно исключить заранее.
   Наличие названия и schema подтверждает лишь объявленную возможность,
   а не успешную работу операции с данным аккаунтом.
8. Следующий безопасный тест — отдельно выбранный и проверенный read-only tool:
   список проектов/страниц либо чтение одной существующей страницы нужного ID.
   Использовать серверный read-only credential, если поддерживается. Не вызывать
   универсальный execute/browser/SQL tool ради простого чтения. `readOnlyHint`
   — подсказка, а не защита. Не читать лишние приватные материалы.
9. Зафиксировать ID правильного проекта и проверить, что сайт не изменился.
   Для доказательства write-возможностей позже потребуется отдельное разрешение
   на один неопубликованный черновик; публикация — ещё одно отдельное разрешение.

Стандартный протокольный discovery не должен менять сайт. Но если неизвестный
сервер имеет побочные эффекты даже при initialize/list, гарантировать это со
стороны клиента невозможно: нужны доверие к реализации и серверное ограничение прав.

## Использование того же MCP в запланированном GitHub Actions

Возможно **условно**, без зависимости от открытого ChatGPT или личного компьютера:

- Сервер доступен по HTTPS из runner и остаётся запущенным независимо от чата.
  Если это stdio-сервер, запускается его проверенная pinned-версия в самом job.
- Авторизация пригодна для unattended use: отдельный ограниченный service token,
  OIDC или поддерживаемый OAuth refresh, а не интерактивный login на каждом job.
  Согласие OAuth для ChatGPT не является токеном для GitHub Actions. У refresh
  credentials может быть ротация — их нужно сохранять в подходящем secret store.
- Client выполняет заранее заданные вызовы с проверенными schemas, без LLM,
  динамического исполнения инструкций сервера или автоматического выбора tools.
- Workflow доступен только доверенной ветке. Секреты — отдельный GitHub Environment,
  permissions минимальны, fork/PR не получает ключей. Не использовать
  pull_request_target для выполнения непроверенного кода с секретами.
- Allowlist конкретных tools, project/page ID и write-параметров; серверные права
  минимальны. Read-only job и publishing job используют разные credentials,
  если сервер это позволяет. Read-only tool whitelist не даёт write-разрешения.
- Durable журнал + атомарный claim + сверка результата защищают от дублей.
  Нет автоматического повтора create/publish после timeout. Cache и локальный
  SQLite на временном runner не заменяют межзапусковое хранилище.
- Скриншоты нужны только если сервер сам работает браузером. В любом случае не
  сохранять cookies/tokens/debug HTTP/полные приватные ответы в artifacts.

Если сервер — обёртка над браузером Tilda, MCP не устраняет истечение сессии,
MFA/CAPTCHA и зависимость от UI. Если использует недокументированные write-endpoints,
MCP не превращает их в официальный Tilda API: выяснить поддержку и сопровождение.
Успех прежних операций в ChatGPT — полезное свидетельство, но не доказательство
поддержки конкретных новых полей/проекта/автономного режима.

- Приоритет — исследовать существующий MCP. Playwright development приостановлен.
- Никакой URL не придуман, сервер не зарегистрирован и соединение не объявлено рабочим.
- Реальные write-инструменты не вызывались. Новый scheduled MCP-workflow не добавлен.
- Имеющееся расписание 1/8 ноября 2026 03:00 UTC остаётся offline dry-run.
- Нужны несекретные данные подключения; затем возможен discovery и read-only тест.
- Автономная публикация остаётся неподтверждённой до отдельного staging write-теста.
