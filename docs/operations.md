# Архитектура, доступы и безопасный тест

## Реализовано

JSON → проверка схемы/уникальности ID и slug → SHA-256 → offline plan.
В core-планировщике сетевого клиента нет. Browser-прототип описан отдельно в browser-prototype.md; его live-target заблокирован. `--publish` всегда запрещён. Ошибки дают ненулевой exit
status и журнал с типом ошибки без текста материала, ключей и ответов сервера.
GitHub сохраняет только план на 14 дней. ID/slug в артефакте также должны быть
пригодны для просмотра участниками репозитория.

SQLite ledger резервирует `(target, article_id)` атомарно, сохраняет digest и
remote ID. Повтор с другим контентом не создаёт новую публикацию: обновление
требует отдельного согласованного пути. После сбоя между отправкой и подтверждением
claim остаётся заблокированным. Нельзя автоматически повторять отправку: сначала
проверить удалённую страницу и восстановить статус. Статус published ставится
только после проверки удалённого ID, URL и содержания будущим адаптером.

Ledger не используется планировщиком: dry-run не должен помечать статьи как
отправленные. SQLite на ephemeral GitHub runner не обеспечивает межзапусковую
защиту. Перед реальной автоматизацией нужен постоянный PostgreSQL/эквивалент с
unique constraint и атомарным claim; concurrency Actions — дополнительная мера,
а не замена БД. Cache/artifacts не считать авторитетным журналом публикаций.

## Доступы (сейчас не подключать)

- Репозиторий: право добавить workflow в default branch; включённый GitHub Actions.
- Для будущего read/export: Tilda public/secret API keys и project ID, API-доступ
  соответствующего тарифа. Хранить ключи как `TILDA_PUBLIC_KEY`,
  `TILDA_SECRET_KEY` в GitHub **Environment Secrets**, не в файлах/контенте.
  `TILDA_PROJECT_ID` — Environment Variable. Эти ключи не дают write-методы.
- Для cloud browser: отдельный пользователь с минимальными правами к тестовому
  проекту, согласованный вход/MFA, зашифрованная сессия в защищённом хранилище.
  Cookies/storage state — секреты; не сохранять в artifacts или git.
- Для внешнего хостинга: отдельный staging-сайт, ограниченный deploy token либо
  OIDC, права на DNS при необходимости. Для БД — отдельные staging credentials.

Будущий live-job должен использовать GitHub Environment `tilda-staging`
с required reviewer (если доступно на тарифе), минимальные permissions и явный
ручной запуск. Production environment завести отдельно. Не передавать секреты
в PR workflows и сторонние Actions без необходимости. URL с ключами не писать
в логи; HTTP debug выключить. Текущие workflow вообще не читают secrets.

## Порядок безопасного теста

1. Справка API/T123/SEO при повторной проверке прочитана; уточнить тариф, доступ к редактору и условия browser automation.
2. Текущая выбранная цель: страница непосредственно в Tilda; внешний хостинг исключён пользователем.
   Для Tilda browser-прототипа отдельно согласовать доступ и условия.
3. Создать владельцем отдельный тестовый проект/страницу с уникальным slug,
   исключить её из меню/sitemap, поставить noindex. Noindex не защищает данные:
   только синтетический контент, при необходимости ограничение доступа.
4. Реализовать и проверить адаптер и общее долговечное хранилище. Для HTML
   добавить allowlist-санитизацию, запрет скриптов и проверку ссылок.
5. Добавить staging credentials через GitHub Environment Secrets и ручное
   подтверждение. Явно разрешить ровно одну тестовую цель, проверить dry-run.
6. Ручной единичный тест после отдельного согласования: сверить страницу, текст,
   код ответа, метаданные и remote ID. Смоделировать timeout после записи,
   повторный запуск, параллельные запуски; дубль не должен появиться.
7. Проверить удаление/откат тестовой страницы. До принятия результатов не
   добавлять live-job к расписанию. Даты в текущем workflow запускают лишь план.

Расписание: cron `0 3 1,8 11 *` + проверка 2026 года. Часовой пояс расписания UTC;
в Новосибирске это 10:00 (UTC+7). Проверка использует фактическую дату runner;
при переносе запуска на следующий UTC-день он безопасно пропускается.
После 2026 года workflow следует удалить/отключить; сейчас будущие годы no-op.
В публичных неактивных репозиториях GitHub может отключать schedule; контролировать
историю Actions и предусмотреть ручной dry-run. Точное время не гарантируется.
